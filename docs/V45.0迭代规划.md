## 一、项目现状分析

### 1.1 现有工单功能（V1.0 基础版）

**后端模型** `backend/db/models/work_order.py`：

| 字段 | 类型 | 说明 |
|------|------|------|
| fid | VARCHAR(64) | MD5主键 ✅ |
| fec_id / fproject_id | VARCHAR(64) | 数据隔离 ✅ |
| order_no | VARCHAR(32) | 工单编号 |
| type | VARCHAR(32) | 工单类型（报修/投诉/装修/访客/放行/其他） |
| title | VARCHAR(256) | 标题 |
| description | TEXT | 描述 |
| level | VARCHAR(16) | 紧急程度（紧急/普通/低） |
| status | VARCHAR(32) | 状态（待派单/处理中/已完成/已取消） |
| assignee_id/name | VARCHAR(64) | 指派人 |
| reporter_name/phone | VARCHAR | 报单人信息 |
| completed_at | VARCHAR(20) | 完成时间 |
| rating | INT | 评分 |
| images | VARCHAR(1024) | 图片URL |

**后端服务** `backend/service/work_order_service.py`：
- `list_work_orders` - 分页列表（status/level/keyword/enterprise过滤）
- `create_work_order` - 创建工单
- `assign_work_order` - 派单
- `complete_work_order` - 完成工单

**API路由** `backend/api/work_order_routes.py`：
- `GET /api/work-orders` - 列表
- `GET /api/work-orders/{fid}` - 详情
- `POST /api/work-orders` - 创建
- `POST /api/work-orders/{fid}/assign` - 派单
- `POST /api/work-orders/{fid}/complete` - 完成

**前端页面**：
- `business-admin/workorders.html` - 管理端工单列表（tab切换/搜索/派单按钮）
- `business-userH5/list.html` - 住户端工单列表
- `business-userH5/detail-repair.html` - 工单详情
- `business-userH5/form-repair.html` 等 - 表单提交页

## 二、系统架构设计

### 2.1 参照规范

依据《Python+MySQL项目设计V2.0》规范：

```
配置层(config/) -> 基础层(db/base.py) -> 模型层(db/models/) -> 工具层(utils/) -> 业务层(service/) -> 入口层(api/)
```

**强制约束**：
- 所有表含 fid(MD5主键) + fec_id + fproject_id + 时间三字段 + is_deleted 软删除
- 全程 SQLAlchemy ORM，禁止原生 SQL
- 统一返回 {code, message, data}
- 环境分离 .env.dev / .env.test / .env.prod
- 命名：t_模块_含义，字段 f 开头

### 2.2 新增模型层规划

```
backend/db/models/
├── work_order.py          # 现有->扩展字段
├── work_order_type.py      # 工单类型定义（EBA/FM/AI/人工等）
├── work_order_category.py  # 工单分类树
├── work_order_template.py  # 工单模板/SOP
├── work_order_log.py       # 工单操作日志（时间线）
├── work_order_rule.py      # 工单规则（超时升级/自动派单）
├── work_order_periodic.py  # 周期工单配置
├── staff_skill.py          # 员工技能标签
├── staff_team.py           # 专业组/班组
├── work_order_classify.py  # 分类记录（自动/人工）
├── work_order_escalation.py # 升级记录
├── area_code.py            # 一区一码配置
├── process_definition.py   # 流程引擎-流程定义
├── process_instance.py     # 流程引擎-流程实例
└── process_node.py         # 流程引擎-节点定义
```

const CACHE_NAME = 'workorder-offline-v1';
const OFFLINE_DB = 'workorder-offline-db';

// 离线时工单操作入队
async function queueOperation(op) {
  const db = await openDB(OFFLINE_DB);
  await db.add('operations', { ...op, timestamp: Date.now(), synced: 0 });
}

// 网络恢复后同步
async function syncOperations() {
  const db = await openDB(OFFLINE_DB);
  const pending = await db.getAll('operations', { synced: 0 });
  for (const op of pending) {
    try {
      await fetch(op.url, op);
      await db.put('operations', { ...op, synced: 1 });
    } catch (e) {
      // 失败继续保留，下次重试
    }
  }
}

## 八、实施建议

### 8.1 迭代策略

1. **第一期先行**：工单基础功能是所有后续功能的地基，建议优先完成
2. **敏捷交付**：每期内部再拆分为 2 周一个 Sprint，可独立上线
3. **灰度发布**：新功能先对单一园区灰度，验证后再推广
4. **数据隔离**：从第二期开始，所有新表按 fec_id/fproject_id 严格隔离

### 8.2 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 流程引擎复杂度高 | 可能延期 | 使用 BPMN.js 开源方案，减少自研工作量 |
| AI 分类准确率 | 业务可用性 | 设置人工复核环节，置信度低时强制人工确认 |
| 钉钉 API 限制 | 集成不稳定 | 本地缓存排班数据，API 失败时走兜底逻辑 |
| 离线数据冲突 | 数据一致性 | 采用 Last-Write-Wins + 人工确认双重机制 |
| 400 人天规模 | 项目管理难度 | 分期交付，每期定义清晰 DoD |

### 8.3 后续扩展方向

- **K2流程平台对接**：将工单审核流程对接到 K2 BPM
- **悦品质历史数据迁移**：300人天实施工作量的历史工单数据迁移
- **微信小程序**：将住户端功能小程序化
